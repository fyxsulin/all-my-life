# 第 1 讲: Rust 如何调用 C 函数

## 为什么要学习这节内容

在学习如何使用 Rust 操作 FFmpeg 之前，首先掌握 Rust 调用 C 语言函数的基础是非常重要的。FFmpeg 是一个功能强大的多媒体处理库，它的核心是用 C 语言编写的，而 Rust 作为一门现代化的系统编程语言，提供了与 C 语言互操作的能力。这意味着我们可以直接在 Rust 中调用 FFmpeg 的 C 语言函数，而不需要完全从头实现相同的功能。

通过学习如何调用 C 语言函数，你将不仅能够充分利用像 FFmpeg 这样已经成熟的 C 语言库，还能在不牺牲 Rust 的安全性和性能优势的前提下，扩展 Rust 项目的功能。掌握这项技术将为你后续深入 FFmpeg 的 Rust 开发打下坚实的基础，让你能无缝集成两者的强大功能。因此，学习这节课是后续开发的基础，也能帮助你理解 Rust 与 C 语言生态系统的互操作性。

## 了解 Rust 和 C 的特性

- **Rust**：以**内存安全**和**高效性能**著称。通过其独特的所有权系统，Rust 能有效避免 C 中常见的内存泄漏、悬空指针等问题，并提供与 C **相当的性能**。
- **C** ：凭借其**高效的性能**和广泛的应用，成为系统编程、驱动开发等领域的基础语言，经过多年发展，C 拥有大量成熟的库和解决方案，广泛应用于各类底层项目。

## Rust 为什么要调用 C 函数?

- **技术债务与现实需求**
  在很多项目中，历史遗留的代码和系统通常是用 C 或其他语言编写的。要完全用 Rust 重写这样的大型系统不仅成本高，而且风险大。因此，利用 FFI 来调用现有的 C 库成为一种现实而高效的选择。这种逐步迁移或混合使用两种语言的方式，能够平衡开发效率和维护成本。
- **生态系统的互补性**
  不同语言都有各自的成熟生态系统。C 的库和框架经过数十年的发展，拥有广泛的应用，而 Rust 由于相对较新，尽管正在快速发展，但在某些领域还未形成完整的库支持。通过调用 C 的库，Rust 开发者可以迅速利用现有的解决方案，而不必等待新的库。

## Rust 如何调用 C 函数?

要在 **Rust** 中调用 **C 函数**，需要使用 **FFI（外部函数接口）** 来实现。

### Rust 调用 C 函数的具体步骤

1. 编写 C 函数

   首先，我们需要定义一个简单的 C 语言函数，例如一个返回两个整数相加结果的函数。

2. 编译 C 代码为库文件

   C 语言函数需要编译为静态库或共享库，以便与 Rust 代码链接。

3. 在 Rust 中声明外部函数

   使用 `extern "C"` 关键字，在 Rust 中声明 C 的函数接口。

4. 在 Rust 中调用 C 函数

   使用 `unsafe` 块调用 C 函数，因为 Rust 无法保证外部函数的内存安全。

#### 1、编写 C 函数

编写一个简单的 C 函数, 将它保存为 sum.c 文件.

```c
#include <stdio.h>

int sum(int a, int b) {
    return a + b;
}
```

#### 2、编译 C 代码为库文件

接下来, 将 C 文件编译为共享库 (Linux/MacOS 下为 .so/.dylib, Windows 下为 .dll)。

在 Linux 或 macOS 上运行以下命令:

```bash
gcc -c -fPIC sum.c -o sum.o
gcc -shared -o libsum.so sum.o
gcc -dynamiclib -o libsum.dylib sum.o
```

这会生成一个名为 libsum 的共享库文件。

#### 3、在 Rust 中声明 C 函数, 并调用 C 函数

可以在 Rust 中使用 `extern "C"` 声明这个 C 函数。确保 Rust 可以找到链接的 C 库。

```rust
#[link(name = "sum")]
extern "C" {
    fn sum(a: i32, b: i32) -> i32;
}

fn main() {
    let a = 5;
    let b = 7;

    // 调用 C 函数需要放在 unsafe 代码块中
    unsafe {
        let c = sum(a, b);
        println!("{} + {} = {}", a, b, c);
    }
}
```

## 关键代码解读

```rust
#[link(name = "sum")]
extern "C" {
    fn sum(a: i32, b: i32) -> i32;
}
```

这段代码是 Rust 中的一个声明, 用于链接外部 C 函数.

1. #[link(name = "sum")]
   - 这是一个属性宏(attribute macro), 用于指示 Rust 编译器在链接时寻找名为`libsum`的库。
   - 该属性告诉编译器, 在链接过程中需要使用的动态库或共享库是`libsum.so`或`libsum.dylib`（根据不同的操作系统, 扩展名可能不同）
   - 这段代码在 Rust 中是必须的, 以确保编译器知道要链接哪个外部库.
2. `extern "C"`:
   - 这个声明指定了接下来的函数是使用 C 语言的调用约定（calling convention）进行定义的。
   - C 的调用约定确保 Rust 编译器生成与 C 编译器兼容的代码, 使得 Rust 可以调用 C 函数。
   - `extern "C"` 的使用非常重要, 因为不同语言之间可能会有不同的调用约定（例如参数传递方式、栈桢布局等）, 这会影响函数调用的正确性。
3. fn sum(a: i32, b: i32) -> i32;
   - 这是函数的声明, 表示有一个名为`sum`的函数, 接受两个`i32`类型的参数, 并返回一个`i32`类型的值。
   - 这里的`fn`是用于定义函数的关键字, 后面跟着函数名`sum`和参数列表`(a: i32, b:i32)`, 以及返回类型 `-> i32`。

### 总结

整体上, 这段代码的作用是告诉 Rust 编译器:

- 在链接时查找名为`libsum`的库, 系统会查找标准库路径(如`/usr/lib` 和 `/usr/local/lib`)中的动态库。如果库不在标准路径中, 您可以使用`DYLD_LIBRARY_PATH`环境变量来指定额外的库搜索路径。
- 该库中包含一个名为`sub`的 C 函数, 这个函数接受两个整数参数并返回一个整数值。
- 函数的调用约定是 C 的，因此 Rust 在调用这个函数时会生成符合 C 调用约定的代码, 从而保证正确性。

在 Rust 中使用这样的声明, 可以方便地调用已有的 C 语言库, 从而实现跨语言的功能集成。

## 扩展阅读

### 了解 .c、.o、.so/.dylib、.a 文件

**.c、.o、.so 文件** 是不同阶段的代码形式.

- **.c 文件: 源代码文件**

  - **含义: **是用 C 语言编写的源代码文件，包含了程序的实际逻辑和实现。它是程序开发者编写和维护的主要文件。
  - **用途: **开发者编写代码时的文本文件，后续需要通过编译器将其转换为机器能够执行的格式（例如 `.o` 文件）。

- **.o 文件: 目标文件**

  - **含义: ** 是**编译后**的目标文件，它包含了源代码经过编译器编译后的机器码，但尚未链接。它是中间产物，无法直接运行。

  - **生成方式: **使用编译器（如 `gcc`）将 `.c` 文件编译为 `.o` 文件。
  - **用途:** `.o` 文件常用于分模块编译，即程序的每个模块分别编译成 `.o` 文件，之后通过链接器组合成最终的可执行文件或库。

- **.so/.dylib 文件: 共享库文件**

  - **含义: ** 是**共享库**（Shared Object）文件，它是编译完成后动态链接库的最终产物。共享库可以在多个程序之间共享，允许程序在运行时动态加载它，而不必在编译时嵌入全部代码。
  - **生成方式: ** 通过编译器（如 `gcc`）将 `.o` 文件链接为共享库文件。例如，`libsum.so` 是一个共享库文件，表示动态链接的 C 函数库。
  - **用途: ** `.so` 文件是可以在多个程序之间动态链接和共享的库。在程序运行时，动态链接器会找到这些 `.so` 文件，并将它们加载到程序的内存空间中，以减少静态链接时的内存使用和磁盘空间。

  - **.a 文件: 静态库文件**
    - **含义: **是一种归档文件，内部包含了多个编译后的目标文件（`.o` 文件）。它们代表了一个库的功能集合，这个库可以包含多种功能、函数或模块。
    - **生成方式: **由多个 `.o` 文件打包而成。使用 `ar` 工具（归档工具，archive）可以将多个目标文件打包为一个静态库文件。

### 了解 C 的静态库和共享库

### 了解 gcc -fPIC 编译器选项

-f 是 GCC 编译器中的一个前缀，表示**编译器选项的启用或控制**，通常用来启用特定的功能或行为。具体到 `-fPIC`，这个 `-f` 表示启用`PIC`。

PIC（Position Independent Code）选项用于生成位置无关代码。这意味着生成的代码不依赖于特定的内存地址，可以在内存的任何地方执行。这对于共享库（`shared libraries`）来说是非常重要的，因为共享库在加载时，可能会被加载到内存中的任何位置，而不是固定的内存地址。

- **`PIC` 的作用**

  - **生成位置无关代码**

    使用 `PIC` 编译时，生成的代码可以在内存的任意位置执行，而不依赖固定的内存地址。这使得共享库在不同程序加载时可以在不同内存地址上正确执行。

  - **动态链接库的需求**

    如果你在编译**共享库**（如 `.so` 文件时），通常需要使用 `PIC`。这是因为共享库需要能够被多个进程或程序同时加载，位置无关的代码能够确保其在不同的进程地址空间中正确工作。

  - **减少重定位**

    使用 `PIC` 编译的代码会减少运行时的重定位操作，从而提高效率。这对于某些架构和性能敏感的应用程序来说是至关重要的。

- **可以不用 `PIC` 吗？**

  - **静态库**（`.a` 文件）：如果你生成的是静态库（如 `.a` 文件）而不是共享库，`PIC` 通常不是必须的。静态库在编译时会直接嵌入到程序的可执行文件中，不涉及动态加载，因此不需要位置无关代码。
  - **共享库**（`.so` 文件）：如果你要编译的是共享库，通常必须使用 `PIC`。如果不使用它，生成的共享库在加载时可能会出现重定位错误或效率低下。

- **如果不使用 `PIC`，会有什么问题？**

  - **共享库可能无法正确加载**：不使用 `PIC` 编译的共享库在加载时，可能会遇到重定位错误，因为这些库需要依赖特定的内存地址。

  - **运行时性能问题**：不使用 `PIC` 编译的共享库，系统在加载时需要进行更多的重定位，可能会导致运行时效率降低，尤其是在高并发和多进程的环境下。

- **总结**

  - **`PIC`是编译共享库时必需的**，它确保代码可以在不同的内存位置加载并运行。

  - 对于静态库或单独的可执行文件，`PIC` 不是必须的，但对于共享库则是必要的。

  - 如果编译共享库而不使用 `PIC`，可能会导致加载失败或性能问题。
